# 本批提取计划

目标是为独立2025模型提供同口径的职住人口、分时通勤与验证计数，保持原模型和2022复现输入。首轮完成对齐与单日pilot，再扩展到目标周和全月。

## 数据对象

| 对象 | 核心粒度 | 服务于模型的什么内容 |
| --- | --- | --- |
| joint职住人数N | 原模型grid_home×grid_work×同一样本 | 居住/工作边际、长期配置和需求反演 |
| 分时Q | date×slot30×实际方向OD×purpose×mode×rail_detected×sample×od_basis | 出发时点、参与率与分时路由 |
| RN压力 | passage_date×slot10×RN pair×purpose×mode×sample | 验证link passage，区分通勤与背景负荷 |
| 逐日参与 | 固定joint OD×day×HW/WH×sample/mode | 月人数到实际日需求的转换，不用月内至少一次替代每日出行 |
| 覆盖QC | 阶段×日期×损失原因 | 缺失、冲突、mask、抑制和来源日边界 |

## 执行次序

1. 只读探针。字段名、move_rn覆盖、RN时钟限制已由Speed回答；本批只交0006（单日trip时钟与端点完整性）、0008（时间fixture）、0009（空间函数）、0010（Speed passage库存）。没有认证或能力时保留SQL与真实错误，不创建伪状态。
2. 0020上传不含个人信息的原网格与合成点，按SubwayMobility NG65U做法用 `CREATE TABLE … AS SELECT stack(n, …)` 分段上传（每段约700行、约100KB），每段末尾一条计数SELECT核对行数。实测点落面；原网格数学结构用于候选索引，裁剪多边形决定最终归属。测试通过后才构造个人点的内部映射。
3. 0100独立月度POI/person，0110独立trip键和purpose。对来源项目已存在表只做只读benchmark，不重跑其任务。
4. 0120构造N；0130构造分时Q与参与率。先pilot 20250519，保留HW/WH不同方向和同格；月度N、19个普通工作日Q与5日验证Q各有自己的日期口径。
5. 0140审计RN来源日、日期键、候选route、时钟。若0010确认Speed passage表仍在，经过日d取来源日d与d+1两张表（Speed 20号任务同规则），以uid+date+moi_id接本项目trip与purpose，只读不改Speed表；Speed候选过滤外的本项目trip单列为缺口，不当作零经过。表已删除时才自行从move_rn按日构造，并先估算存储。0150建立与Q相同trip universe的purpose压力，再做mask内和全部候选压力对照。全体mode1单独作为背景/覆盖对照，不混入R通勤。
6. 0300闭合与损失QC；0500按pilot实测行数/字节制定容量，再0400逐份导出并验收。Speed全市全周10分钟RN pair压力已用389份、约3.06GB；再按purpose×sample拆分会成倍增加，0500须比较“上传RN pair→模型连接映射后在平台聚合到模型连接”的方案。

这些编号对应queue.json的19项依赖。正式build SQL在上游核实后生成，不能直接提交空模板。版本、数据期、样本、字段与来源SQL哈希必须同时冻结。

## 初始需求与最终可观测性

先同时提取主点职住OD和实际trip端点OD的QC。主点是长期配置对象，实际端点更接近道路路由；两者需要od_basis标签，不能混为一个矩阵。actual_trip端点依赖start_poi/end_poi与同人当月POI的唯一关联；不可用时明确标为缺失，只完成有依据的主点HW/WH需求。

非通勤Q需要实际端点支持。若仍缺端点，沿用Speed既有七列细OD作独立描述，不伪造“通勤之外”的3公里矩阵。RN聚合可先按purpose比较，不必等待所有非通勤端点恢复。

## 模型接入顺序

提取后在data_work建立新model_input版本，固定供给和mask，先比较2022与2025静态需求，再增加AM/PM，最后30/60分钟。所有时段共用长期职住人口，不能各时段重复计人或简单相加独立GE福利。RN若参与校准，留出日期/道路，不把同一拟合叫外部验证。
